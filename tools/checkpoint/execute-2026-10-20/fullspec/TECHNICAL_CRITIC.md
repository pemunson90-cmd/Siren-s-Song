Material findings, ordered by technical consequence rather than global campaign priority:

**T1 — High; reliable progression blocker under storage failure; inherited correctness defect.** game/src/main.gd:617–621 handles a failed save by assigning store.warning to sim.message. _show_campaign at 410–438 displays neither that warning nor unsaved status; loading warnings take the same message-only path at 639. A disposable real-Main probe forced FileAccess.open failure using a missing directory: warning and sim.message both became “Unable to write archive. Check device storage.” After returning to operations, no visible menu Label contained it and log_label was hidden. This is the same write-open failure branch as unavailable storage, not a physical disk-full experiment. Recovery/incompatible-archive warnings are likewise not represented in the operations menu by source inspection.

Player consequence: the player can leave or launch another operation believing progress was saved when only memory contains it. Atomic backup protects prior data but cannot preserve the latest unwritten progress. Expected quality: persistent, truthful unsaved/recovery status across screens and lifecycle transitions. Remedy: retain an unsaved state/error independently of transient mission messages, expose it in operations, offer an ordinary retry, and clear it only on a verified successful save. Preserve existing atomic/backup behavior. This is failure handling, not new save validation/schema/legacy compatibility. It does not make the unrelated PR41 change a regression.

**T2 — Medium-high; startup/content-delivery expansion.** OceanView._ready builds 384,000 image pixels synchronously (game/src/presentation/ocean_view.gd:33–46). Soundscape._ready synchronously synthesizes 20 one-shot samples and two loops (audio/soundscape.gd:20–87,93–103) before Main can finish initialization. In an imported disposable c2db archive, loading/instantiating/readying actual Main took 4,246.6 ms; separate component runs measured 882.1 ms water and 1,050.1 ms sound readiness. These are host elapsed measurements, including loading and scheduling; separate runs are not additive decomposition or Android timings.

Player consequence: launch has substantial main-thread work before a responsive game frame. Main has no staged application loading path around these jobs (73–120); an engine splash may precede Main and was not assessed. Expected quality: prompt visible response and bounded interactive-thread work. Remedy: prepare/cache deterministic original texture/audio content during authoring/export, or stage its preparation behind a first responsive loading frame. Keep the generated identity and deterministic audio; do not add a new loading framework or infer an Android ANR from this host measurement. Startup remains a performance opportunity, not a demonstrated device crash.

**T3 — Medium-high; sustained performance expansion, native result open.** Sensor pulses call _observe every 0.15 s (simulation/simulation.gd:679–681). Tutorial maps without world_size (including measured IDs 0/3/5) scan all 960 cells and call visible for each even when cells were previously known (871–881); region-authored maps, including expanded Split Channel, already use bounded WorldRegion.observation_cells (world_region.gd:34–52). 60 repeated actual _observe calls at ordinary starts measured medians 7.44/8.89/7.89 ms for IDs 0/3/5, with p95 about 26.8/28.2/27.5 ms; ID 11 median 0.55 ms and p95 0.79 ms. A separate 180-tick/start probe across all 14 missions had no script errors; ID 3 tick p95 ~16.0 ms/max 32.2 ms, ID 5 max 39.9 ms, before UI/rendering. These Time.get_ticks_usec measurements include host scheduling/contention and are neither CPU-cycle profiles nor FPS certification.

Player consequence: recurring synchronous sensing leaves less of a 16.7 ms frame budget for input/rendering; catch-up can add more ticks (642–646). Expected quality: measured stable target-device frame pacing, with the documented 30 fps/effects fallback when needed. Remedy: profile/bound sensing work using existing receiver-disk machinery or safe caching, preserving every contact refresh and legacy survey’s whole-map semantics. Measure a matched baseline/challenger; do not blindly slow sensing or spread tactical truth across unfair delays. No fallback quality selector/adaptation exists in current project/Main settings. Native GPU cost, full-dive thermal/battery behavior and fallback effectiveness remain unverified; this is not a mandate for broad speculative optimization or an automatic APK.

**T4 — Medium; accessibility/alternative-input expansion.** Main._button forces FOCUS_NONE at main.gd:133; route_program_panel.gd:26 does likewise. In actual startup operations, four enabled visible buttons had zero focusable controls, and injected Tab left focus null. Main’s key handling offers Space/Escape, not menu traversal (384–393). Settings expose audio only (640–650); font sizing derives from density/touch height (122,160–172), with no independent text-size preference. Canvas craft/contact drawing has no equivalent application-provided focusable map-target interface.

Player consequence: keyboard-style traversal cannot operate even the first operation menu, restricting alternative input; low-vision players cannot enlarge reading text independently of the chart. Expected quality: usable non-pointing menu/planning navigation and adjustable readable text without shrinking targets or displacing essential actions. Remedy: preserve touch ownership while enabling predictable focus/activation/back behavior and meaningful selected-craft/status alternatives; add text scaling with real reflow. Android TalkBack/SwitchAccess, OS font scaling and physical ergonomics were not exercised: no blanket claim that those services fail. This is commercial accessibility scope, not a new requirement to add a controller scheme during Pass 0 or a reason to prioritize UI polish above unfinished operations.

**T5 — Lower priority; audio resilience/quality, experienced frequency open.** The five-voice allocator accepts only an idle player and otherwise silently returns (soundscape.gd:104–111,144–149); event dispatch then clears all events (134–143). A controlled actual-component probe filled all five voices with creak streams, requested loss, and observed five active voices with no loss stream. This proves no critical-cue reservation/preemption, not that five creaks naturally occur or that campaigns commonly lose this cue. Visual loss feedback remains.

Player consequence: a consequential semantic cue can be discarded during voice pressure. Expected quality: bounded polyphony with important loss/threat/received cues protected from decorative sounds. Remedy: reserve or preempt by existing cue importance and avoid repeated decorative occupancy; validate an actual plausible event collision before increasing priority. Root accepts the mechanism and leaves gameplay frequency/experienced impact unmeasured. Later quality work, not a PR41 blocker.
