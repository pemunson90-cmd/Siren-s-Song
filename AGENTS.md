# Siren's Song — Gauntlet operating instructions

## The objective
**Continually evaluate the whole playable game; identify its most consequential weakness or opportunity; improve it; evaluate the result; repeat.** This is the original Gauntlet mandate, not a newly discovered feature. Look across mechanics, player decisions, missions, atmosphere, art, sound, enemy behavior, campaign progression, controls, technical quality and missing depth. A completed task, review, plan, APK, six-mission campaign or apparently polished release is a milestone, not a stopping point. The user alone decides when the Gauntlet ends. Seek AAA-caliber and commercially publishable-*quality* game content and execution, without store administration, marketing or legal publishing tasks.

**Work on the game, not on proving that a workflow happened.** Pick improvements by their expected effect on the player's actual experience. Question accepted approaches when a larger gain is available. Prefer deep, coherent gameplay and polished, intuitive interactions to more granularity, test counts, ceremony or endlessly decorating existing assumptions.

Communication: state concrete actions, results and intended player gains directly. Explain limitations when they affect an actual expectation, with the reason. Keep progress updates affirmative and concise.

## Authority
Current user decisions > `docs/CURRENT_GAME_SPEC.md` and accepted amendments > ratified design bible/selected visual decisions > demonstrated play/source evidence > historical provenance > proposals. `docs/SOURCE_AUTHORITY.md` resolves details. The playable v7 source is a working implementation reference: do not lose its demonstrated knockdown weapon, Hunt, acoustic footprint, environmental systems or other mechanics without deliberate comparison and rationale. Old single-level specs, wrappers, approval loops and historical work plans are archival evidence, not present instructions.

For current work read `docs/CONTINUATION.md` (active workers/next action) and `docs/WORKBENCH.md` (compact status). `docs/V7_TO_GODOT_PARITY.md` tracks purposeful implementation differences. `docs/architecture/GAUNTLET.md` is technical architecture, not a second Gauntlet policy.

## The development loop
1. Assess the *whole* current game and rank the biggest experiential weaknesses and promising opportunities against the project's identity and strong relevant games.
2. Research existing implementations and useful patterns before creating custom systems. Select the most valuable coherent next design; define a concrete player-facing gain, not a checklist of output files.
3. Develop each independently mergeable design on its own branch/worktree with clear ownership. Parallel nonconflicting development should keep moving.
4. **One designated integration reviewer** checks the diff against current production, gameplay consequences, conflicts, save/source fidelity and *relevant* focused tests; request another specialist only for an identified distinct high risk.
5. The sole integrator reconciles approved work with the latest `gauntlet/production`, preserves a playable baseline and fixes confirmed consequential regressions. Use focused tests and real Godot play/previews locally or through GitHub by default. Batch broad Godot regression at meaningful milestones. The user prefers fewer APKs: do not automatically build Android packages for milestones; build only on explicit user request or when a concrete Android-specific risk cannot be resolved in Godot. Finish inspecting existing artifacts without rerunning CI for retrieval.
6. Decide what meaningfully improved, what was sacrificed, and the next biggest gap. Immediately continue the loop and dispatch useful work. Independent critics periodically assess the whole experience, not merely the last changed button.

A worker can finish its assignment; that does not finish the Gauntlet. Do not request routine owner approvals, wait for an APK for each change, rerun identical suites, produce mandatory comparative clips for each small merge, or create gratuitous second-reviewer gates. Never merge known broken game/save behavior. Preserve rejected approaches where they teach something useful.

## Required task closeout and guidance maintenance

**The Gauntlet has no agent-controlled completion state.** Each time a worker, reviewer, bounded plan or milestone ends, root collects its result, performs the designated review/reconciliation or assigns a reviewer, checks the current governing files and handoffs for staleness, and **starts or delegates the next highest-value authorized improvement** while tools and usage permit. Task completion must not become an orchestrator farewell or an excuse to await the user. Root owns cross-worker delegation even after individual workers end. Only the user can terminate the Gauntlet.

**Mandatory staleness gate after each task:** run `python3 scripts/toolchain/gauntlet-boundary.py --boundary complete`, which fetches the latest production instructions and runs a read-only structural guidance check. Then semantically compare current user decisions, living game requirements, the design bible, visual concept selections and handoffs, active branch ownership, latest review results, actual CI evidence, CONTINUATION and WORKBENCH. Repair simple obsolete status/authority references as an agent-owned documentation task on a separate feature branch; preserve immutable provenance and other workers' edits. A linter's passing result is only a structural check, not proof of correct design or fresh active ownership. Never ask the user to update ordinary project documents. A failed/stale check triggers a specific repair task and review, not Gauntlet termination.

**Integration and accepted baseline:** feature branches/worktrees from latest `gauntlet/production` get relevant fast/targeted checks and one designated reviewer, then root reconciles changes by PR or reviewable equivalent. `gauntlet/production` is the continuously integrated playable development line; **`main` is the protected accepted baseline**, updated by deliberate tested promotion PRs from production at coherent milestones. A production merge is not by itself a `main` promotion. Do not force-push either shared branch, bypass a failed check or merge known-broken game/save behavior. Keep all active branches intact.

**Execution availability:** only actual usage/platform execution exhaustion or an explicit user stop can interrupt dispatch. If an enforced limit ends the available session, checkpoint exact SHA, branches, owners, relevant evidence and first resumption command, mark **PAUSED — RESUME REQUIRED** and resume the loop when execution is available. Repository hooks cannot invoke an agent after its session is gone; never claim invisible background execution.

## Source, platform and model discipline
- Project: original Android-first 2D tactical submarine reconnaissance game, one Quietus pilot and two drones; continuous simulation with unlimited tactical pause, limited sensing, acoustic exposure and physical navigation. Godot 4.6.3 / GDScript / Compatibility; game in `game/`. The existing six authored missions form the introductory/tutorial arc. The intended game is a substantially longer, involved campaign with branching story routes inspired by Star Fox, meaningful Quietus and drone upgrades, story development and multiple endings. AAA-caliber Android quality is a serious target across the whole experience, not rhetorical shorthand. Preserve source and user-ratified design identity.
- Keep work from other agents intact. Each worker owns explicit paths/interfaces; root alone integrates/pushes production. Worker completion should release ownership and lead to further development rather than repeated management by the user.
- At task/dispatch/review/merge/resume boundaries fetch and read the latest governing files and pass their SHA and current instructions to workers. Use `scripts/toolchain/gauntlet-boundary.py` and `docs/GAUNTLET_ORCHESTRATION.md`. Actually apply the updated documents, not merely print a receipt.
- Default substantial worker/reviewer routing when selectable: `gpt-6.1-sol`, fresh context. Fit-to-task smaller agents are permitted. Astra/premium is reserved for exceptional architectural consequences or a demonstrated impasse, not default subagents. Record actual observable routing faithfully without treating usage bookkeeping as a gameplay milestone.
- Preserve the established Git-tracked **development** keystore and signing identity under `scripts/toolchain/signing/`; do not regenerate a replacement key due to cache/configuration loss. Production/release signing is separate.

## Keep active Git lean
The working repository is for **game source/assets, tests and build tools, version history, and compact instructions**. Do not write ongoing audit batches, critic reports, work diaries, raw metrics, screenshots, videos or test-output archives into `gauntlet/production`. Preserve them in a recoverable archive outside the active development tree, recording an immutable source SHA and verification hashes. The existing `archive/gauntlet-evidence-2026-10-19` branch preserves the pre-cleanup snapshot; avoid extending an audit-document trail on production. Do not delete dependency-critical data or prototype source without checking tooling and retaining a recoverable copy.

Reuse inactive existing worktrees for new tasks instead of accumulating a new checkout per review or experiment. At meaningful boundaries inspect free disk space and retire duplicate checked-out archival content from confirmed inactive, tracked-clean trees using normal Git checkout while preserving their branch refs and all unique/untracked evidence, saves, caches and signing material. Never force-clean another worker's tree. Keep one shared toolchain; disk housekeeping must not interrupt active game work or become a substitute for it.

Keep `docs/CONTINUATION.md` and `docs/WORKBENCH.md` short: current integrated base, active branch ownership, one or two meaningful weaknesses, current blocker if observed, and next action. Prior details are in Git history or archive. On an interruption, save an exact reproducible checkpoint and next command.
